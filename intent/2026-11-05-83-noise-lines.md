# Intent: Noise does not become transcript lines

## Problem

#14 promised that "silence and noise never become lines". On Parakeet this does not fully hold. #73's guard baseline (`docs/eval/2026-11-call-pipeline.md`), at real speed:

| 5 minutes of | Lines written |
|---|---|
| Silence | 0 |
| Room tone | 1 ("Sh") |
| Non-speech bursts | 16 |

Every line on the bursts is a tiny filler, about a second long: "Yeah." (6), "Uh." or "Uh" (5), "Mm." (3), "Mm-" (1). They appear in the transcript, and can feed notes and answers.

**Not known:** how this translates to real calls. These are MUSAN noise clips placed about a second apart, which is a harsh test. Typing, coughs and doors in a real call may do less, or more. The owner has reported a real English call working well.

**Why it is not simple:** "yeah" and "mm" are also real replies. Filtering these words would remove real speech, and short replies are already a weakness. `MIN_SOUND_SAMPLES` (`src/speech/stt/transcription.rs:400`) only tests loudness, so it can't tell a cough from a word.

## Proposed outcome

- Noise produces far fewer invented lines than today, measured on the same sets.
- Real short replies survive at least as well as today. Bleed, delay and word errors are no worse, using #73's baselines.
- If nothing meets both at once, the result says so, and nothing changes.

## Affected users and systems

Anyone on a batch engine, mainly Parakeet: `src/speech/stt/` and `shell/` only if a setting is needed. Possibly a voice-activity model in the closure, about 2 MB, if one is used. Streaming Deepgram is unaffected.

## Constraints

- **Losing a real reply is worse than an occasional "Uh".** A short reply can carry the meeting's meaning; a stray filler is only clutter.
- **No added delay,** using #73's speech-to-line baselines, per channel.
- **#14's bleed guarantee holds.**
- **Measure first.** A real labelled set of short replies is needed: #73's English short-word guard is weak, since it uses clips of longer sentences.
- **No artificial CPU load on p620,** and tests run only through `shell/tests/` or `tools/accuracy/`.

## Open questions

1. **Is a real-call sample available?** Recommended: if the owner can record a few minutes of ordinary noise, such as typing, with nobody else on it, it would show whether this happens in real use. Otherwise built sets only, with that limit stated.
2. **Which approach?** Left to the spec. Recommended to compare: a voice-activity check before decoding, as NB-Whisper had (Silero, removed in #77); dropping only very short filler lines with low confidence or no neighbouring speech; and doing nothing.
3. **Is doing nothing acceptable?** Recommended: yes, if the owner's real calls rarely show it. Short lines are easy to ignore, and a fix risks real replies.
