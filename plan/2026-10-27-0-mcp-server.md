# Plan: MCP server for nixarchy-meetingai

## Approved decisions (copied from the spec)

- **The process:** `nixarchy-meetingai mcp` is an MCP server over stdio,
  built on `rmcp` 3.8 (pinned). It is a thin client to the daemon socket
  `$XDG_RUNTIME_DIR/nixarchy-meetingai/daemon.sock` (NDJSON:
  `{"id","cmd","args"}` → `{"id","ok","data"|"error"}`, plus events),
  connecting once per call and reconnecting if the daemon restarted. If the
  daemon is down, every tool returns the error "The nixarchy-meetingai
  daemon is not running; start nixarchy-meetingai.service"; the handshake
  still succeeds.
- **Origin:** every MCP request carries `"origin":"mcp"`. The daemon logs
  `tracing::info!(origin="mcp", cmd)` (never the arguments).
- **New daemon commands:**
  - `transcript.get{meeting?, after_line?, limit≤500}` returns
    `{meeting, lines:[{line, who, speaker, text, t0, t1}]}` (`line` is the
    `meeting_lines` rowid; no `meeting` means the current session)
  - `now.get` returns `{status: idle|listening|writing|ready, question,
    answer, provider, model, suggestions}`
- **Consent:** the setting `mcp_allow_record` (bool, default false, a
  normal visible setting) gates `record.start` when `origin=="mcp"`; it is
  refused with "Recording by agents is disabled (setting
  mcp_allow_record)".
- **Notices:** when an MCP request runs `record.start`, `record.stop` or
  `chat.send`, the daemon emits `notice{text}` ("An agent started
  recording", "An agent stopped recording", "An agent asked: <first 80
  characters>"). The overlay shows it as a quiet line.
- **Tools** (each returns a text summary plus structured JSON, with a
  one-line description written for an LLM; mutating tools are annotated
  non-read-only):
  - `meeting_status`: `state.get` + `now.get`
  - `transcript_get{meeting?, after_line?, limit?}`
  - `current_answer`: `now.get`
  - `ask{question ≤ 8k characters}`: `chat.send`, then wait for that turn's
    `answer.done`/`answer.error` (120 s; on timeout return what streamed
    so far with `partial:true`); returns answer, provider, model,
    suggestions
  - `meetings_list{query?, limit?}`: `session.list`, filtered in the client
  - `meeting_notes{meeting}`, `notes_regenerate{meeting}`
  - `session_new`, `session_restore{meeting}`
  - `record_start`, `record_stop`
  - `settings_set{key, value}`: allowlist `meeting_mode`,
    `response_pace`, `chat_provider`, `chat_model`, `live_provider`,
    `live_model`, `text_scale`; `api_key` and `mcp_allow_record` are always
    refused
- **Resources:** `meeting://current/transcript` (the last 200 lines,
  markdown), `meeting://{id}/transcript`, `meeting://{id}/notes`;
  `resources/list` returns the current meeting plus the 20 most recent.
- **Registration** is documented only: a README "Use from AI agents"
  section with `claude mcp add --scope user meetingai --
  nixarchy-meetingai mcp`, `codex mcp add meetingai -- nixarchy-meetingai
  mcp` and `agy mcp add …` (check each command's real syntax with
  `--help`). Nothing in Home Manager writes the clients' config files.

## Repo traps

- Start **after the round-4 UI commit lands** (it edits
  `src/core/models/settings.rs`); rebase on it if needed.
- cargo only via `devenv shell -- <cmd>`. Run rustfmt on your own files
  only (`rustfmt --edition 2024 <files>`), never `cargo fmt` on the whole
  crate.
- Coders cannot commit (guard hook); the lead commits each step.
- Socket paths over 108 bytes fail: tests use a short `mktemp -d
  /tmp/nm.XXXX` runtime dir.
- `src/daemon/session.rs` is large; add the new commands next to the
  existing `handle` match (`session.rs:2034`), not in a new dispatch.

## Steps

1. `Cargo.toml`: add `rmcp = "=3.8.0"` with the server, stdio-transport and
   macros features (confirm the feature names in rmcp's docs through
   Context7 or docs.rs first).
   → verify by `devenv shell -- cargo build`
2. Origin and consent:
   - `src/daemon/protocol.rs:15` `Request` gets `#[serde(default)] pub
     origin: Option<String>`.
   - `src/daemon/server.rs` passes it into `handle` (change the signature
     to `handle(cmd, args, origin)` and update every caller, tests
     included) and logs MCP calls.
   - `src/core/models/settings.rs` gets `mcp_allow_record` (struct,
     default false, keys, load, save, pairs, a round-trip test).
   - `session.rs` `record_start` (around line 1221) refuses
     `origin=="mcp"` unless the setting is on.
   - Emit `notice` for MCP `record.start`, `record.stop` and `chat.send`.
   → verify by unit tests: refused by default; allowed when set; a
   non-MCP origin is unaffected; a notice is emitted.
3. `transcript.get` and `now.get` in `session.rs`, using `db::meetings`
   for stored lines and the in-memory state for the current session.
   → verify by unit tests for paging (`after_line`, `limit` capped at 500)
   and the `now.get` status values.
4. `src/mcp/mod.rs` (new): the rmcp server with the 13 tools and 3
   resource templates from the decisions. It uses its own socket client
   (newline JSON; match events by `turn` for `ask`). Add `pub mod mcp;` in
   `src/lib.rs` and a `"mcp"` arm next to `"ctl"` in `src/cli.rs:17`
   (`src/main.rs` if the async runtime is set up there). Validation:
   length caps (`question` ≤ 8k, `limit` ≤ 500), the `settings_set`
   allowlist checked before any socket call.
   → verify by `devenv shell -- cargo build`, then `printf
   '<initialize>\n<tools/list>\n' | nixarchy-meetingai mcp` lists 13 tools
5. `tests/mcp_flow.rs`: spawn the daemon test server (the existing
   `daemon_flow` seams, a fake provider, a short runtime dir) and the built
   binary's `mcp` with that `XDG_RUNTIME_DIR`. Speak JSON-RPC over its
   stdio and cover the spec's Verification §1 cases: initialize;
   tools/list (13); `meeting_status`; `ask` returns the fake answer and
   suggestions; `transcript_get` with `after_line`; `record_start` refused,
   then allowed after `settings.set` on the socket; `settings_set` refusing
   `api_key` and `mcp_allow_record`; `resources/read
   meeting://current/transcript`; a clean tool error when no daemon is
   running.
   → verify by `devenv shell -- cargo test --test mcp_flow`
6. `shell/Client.qml`: add the `notice` event as a row with `who:
   "notice"`. `shell/Overlay.qml`: render notice rows as one muted caption
   line (no bubble). `shell/tests/fake-daemon.py`: emit one notice in the
   default scenario. `mcp_allow_record` appears in Settings through
   `settings.search` as a toggle labelled "Let AI agents start recording".
   → verify by `bash shell/tests/lint.sh`, `bash shell/tests/smoke.sh`
7. `README.md`: a "Use from AI agents" section with the three registration
   commands (checked with each CLI's `--help`), the tool list, the
   consent setting and the privacy note.
   → verify by reading it back
8. Manual checks (session model, not the coder): register with Claude
   Code; ask "what's the status of my meeting?" and "ask the copilot:
   explain k8s"; check that the overlay shows the notice; run Codex and
   agy reviews per `reviewers:`.

## Rollback

Each step is its own commit on `refactor/omarchy-quickshell-rewrite`;
`git revert` any of them. Removing the `mcp` subcommand and `src/mcp/`
leaves the daemon unchanged apart from the harmless `origin` field and the
two read-only commands. Clients deregister with `claude mcp remove
meetingai` (and the equivalents for Codex and agy).

## Implementation split

Steps 1–7 go to `coder` agents (Sonnet), run as a workflow as the owner
asked earlier. Steps 2 and 3 touch `session.rs` and run in order; step 6
(QML) and step 7 (README) can run in parallel with steps 4–5. The session
model commits each step, then does step 8 and the reviews: a fresh Opus
agent with this path and `git diff`, then Codex and agy.
