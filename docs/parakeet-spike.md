# Parakeet spike (plan step 3, #14)

Question: can Parakeet TDT 0.6B v3 (INT8) run in-process from Rust through
sherpa-onnx, linked against the nixpkgs library, with no build-time download?

Answer: yes. Recommendation at the end.

## What was built

- `Cargo.toml`: optional dependency `sherpa-onnx = "2.0.1"` (the official safe
  wrapper in k2-fsa/sherpa-onnx `rust-api-examples`; NOT `sherpa-rs`), with
  `default-features = false, features = ["shared"]`, behind cargo feature
  `parakeet`. Default build does not compile it.
- `examples/parakeet.rs` (`required-features = ["parakeet"]`):
  `parakeet <model-dir> <16k.wav> [threads] [chunk-seconds]`.
- `nix/parakeet-model.nix`: fixed-output fetch of
  `sherpa-onnx-nemo-parakeet-tdt-0.6b-v3-int8.tar.bz2` (release `asr-models`,
  487 MB, sha256 `5793d0fd...16bf` = the digest GitHub publishes), unpacked,
  `passthru.{encoder,decoder,joiner,tokens}`, `meta.license = cc-by-40`.
  Built with `callPackage`; output 640 MB.

## Linking against nixpkgs sherpa-onnx (key finding)

- `sherpa-onnx-sys` 2.0.1 `build.rs` defaults to feature `static`: it
  downloads `sherpa-onnx-v2.0.1-*-static.tar.bz2` from GitHub at build time.
  That fails in the Nix sandbox.
- Escape hatch: feature `shared` plus env `SHERPA_ONNX_LIB_DIR=<dir>` skips
  every download. It then emits `-lsherpa-onnx-c-api -lonnxruntime`.
- nixpkgs `sherpa-onnx` 1.13.8 has `lib/libsherpa-onnx-c-api.so` but NOT
  `libonnxruntime`; `<dir>` must hold both. Use
  `symlinkJoin { paths = [ sherpa-onnx onnxruntime ]; }` (onnxruntime 1.27.1)
  and point `SHERPA_ONNX_LIB_DIR` at its `lib/`. Verified: builds, and with a
  store-path dir the binary gets a RUNPATH to it and runs without
  `LD_LIBRARY_PATH`. With a non-store dir (/tmp) the Nix cc-wrapper drops the
  RUNPATH (needed `LD_LIBRARY_PATH` for the first runs). The crate's build
  deps (`ureq`, `zip`, `bzip2`, `tar`) still compile but never touch the network.
- Version skew: Rust crate 2.0.1 against C library 1.13.8. The offline
  transducer config struct worked fine (model loaded, decoded, timestamps ok).
  Not checked: other APIs (VAD, online). A nixpkgs bump of sherpa-onnx could
  break this silently; pin by a flake check that runs a tiny decode.
- Real build needs the crate in `Cargo.lock` vendoring (`cargoLock`/`cargoHash`
  in `nix/package.nix` changes). `Cargo.lock` in this worktree is modified
  (sherpa-onnx, sherpa-onnx-sys, and their build deps).
- I did not run a full `nix build` of the package (3 min cargo build each
  time); the dev shell (`nix develop -c cargo build`) built with the
  environment variable only and no sherpa download. Network was available, so
  this is not a sandbox proof for the crates; the download path is the only
  one in `build.rs`, and it is skipped by the env var.

## Measurements (p620-class AMD host, 128 threads, 251 GB RAM, CPU only)

Model files were in the page cache (just extracted); true cold-disk load not
measured (cannot drop caches here), expect +1-2 s for 640 MB.

| Case | Threads | Load | Decode | RTF | Peak RSS |
|---|---|---|---|---|---|
| en 3.8 s clip | 4 | 2.5-2.9 s | 0.32-0.36 s | 0.08-0.09 | 1.1 GB |
| de/es/fr 3-5 s clips | 4 | 2.5-3.7 s | 0.2-0.6 s | 0.08-0.12 | 1.1 GB |
| 30 s TTS clip | 4 | 2.5 s | 2.4 s | 0.080 | 1.4 GB |
| 10 min TTS, 30 s chunks | 2 | 2.3 s | 67 s | 0.112 | 1.8 GB |
| 10 min TTS, 30 s chunks | 4 | - | not run (60 min run below: RTF 0.076) | - | - |
| 10 min TTS, 30 s chunks | 8 | 2.3 s | 33 s | 0.054 | 1.9 GB |
| 10 min TTS, 60 s chunks | 4 | 2.3 s | 49 s | 0.081 | 2.2 GB |
| 10 min TTS, 120 s chunks | 4 | 2.2 s | 56 s | 0.094 | 3.2 GB |
| **60 min TTS, 30 s chunks** | 4 | 12.4 s* | 274 s | **0.076** | **1.7 GB** |
| 60 min TTS, one 60 min decode | 4 | - | FAILED after 6.5 min | - | - |

*the 12 s load was under contention with another run on the shared machine.
Peak RSS includes the decoded WAV in memory (the 60 min file is ~115 MB of f32).

- Idle RAM after load is about 1.1 GB.
- The 60 min file (espeak-ng, 9 800 words generated by repeating 10 sentences
  at 150 wpm, resampled with sox to 16 kHz mono) came back as 9 678 words
  (about 99 %; not a WER measure, TTS is easy audio).
- Whole-file decode of 60 min fails in onnxruntime
  (`Add node ... BroadcastIterator::Init`, attention shape): the encoder cannot
  take an hour in one pass, and cost grows with length (RSS 3.2 GB at 120 s).
  Chunks of 30 s are best: lowest RAM and RTF. This matches the plan's
  per-channel `BatchChunks`.
- Token timestamps: yes. `timestamps.len() == tokens.len()` for every case
  (19 667 for 60 min), start times in seconds from the chunk start on an 80 ms
  grid (0.0, 0.16, 0.32 ...), plus `durations` in the result struct. They are
  per BPE token, not word-level; words need joining by the leading-space
  marker. Chunk offsets must be added by the caller. Not validated against
  ground truth, so "reliable" is still open; no word timing is needed by the plan.
- Languages: English, German, Spanish, French test clips transcribed correctly
  (v3 is multilingual).
- Fallback (`python3Packages.sherpa-onnx` behind an OpenAI-compatible service)
  was not tried: the in-process route worked, so no need.

## Not checked / risks

- Real meeting audio, and accuracy against Whisper (step 5 on p620).
- Cold-disk load, GPU, NPU. CPU only.
- Concurrency: one recogniser decoded sequentially per chunk. A mic and a
  system channel decoding at the same time would share the thread pool; not
  measured. Streams are cheap (`create_stream`), the recogniser is the 1 GB part.
- sherpa-onnx crate 2.x against nixpkgs 1.13.x C API skew (above).
- Attribution: CC-BY-4.0 needs the NVIDIA credit in the About/NOTICE text.

## Recommendation

In-process via the sherpa-onnx Rust crate (feature `shared`,
`SHERPA_ONNX_LIB_DIR` = symlinkJoin of nixpkgs `sherpa-onnx` + `onnxruntime`).
Decode on a blocking worker in 30 s chunks per channel, 4 threads. Budget
about 1.1 GB idle, 2 GB peak, 2.5 s load, RTF 0.08 (a 30 s chunk in about
2.4 s). Keep the service fallback only if the crate/library skew bites later.
